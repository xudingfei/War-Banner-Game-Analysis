# 喵喵的结合：动画演示系统分析

本机检查日期：2026-09-13。对象为 `D:\Game\steamapps\common\Mewgenics\resources.gpak` 内的 SWF 动画及 GON 配置。本篇只保存结构分析、帧数统计和 C++ 风格伪代码，不分发原作动画文件。

**已确认的资源结构是：角色导出元件包含动作标签，各标签对应嵌套的动画片段；技能配置通过动画名称选择表现。** 抽查的三个 SWF 都声明 60 帧/秒的时间轴速率。不能据此断言游戏实际渲染始终为 60 FPS，也不能把一个 SWF 时间轴帧当作一张独立手绘图。

## 1. 这次具体检查了什么

从 GPAK 索引取得文件偏移和长度，只读对应资源区间，检查 SWF 文件头，并解析导出名、`DefineSprite`、`FrameLabel`、`ShowFrame` 及相关对象放置/移除标签。

| GPAK 内部路径 | 签名/版本 | 声明时间轴速率 | 根时间轴帧数 | DefineSprite 数量 |
|---|---|---:|---:|---:|
| `swfs/catanis.swf` | FWS / 17 | 60 FPS | 1 | 812 |
| `swfs/catanis2.swf` | FWS / 17 | 60 FPS | 1 | 245 |
| `swfs/enemies.swf` | FWS / 17 | 60 FPS | 99 | 1742 |

在这三个样本中，片段声明帧数与各自时间轴内统计的 `ShowFrame` 数量一致。根时间轴帧数不能当作文件中所有动作的帧数：根只有 1 帧的文件，仍可以容纳数百个多帧子片段。

SWF 文件头的 `FrameRate` 表达期望播放速率，`DefineSprite` 具有自己的帧计数和控制标签。格式依据为 [Adobe SWF File Format Specification v10（镜像）](https://www.flashrealtime.com/content/dam/Adobe/en/devnet/swf/pdf/swf_file_format_spec_v10.pdf) 的文件头、DefineSprite 和控制标签说明；本机文件为版本 17，本次使用的是其中这些基础结构。Adobe 也把文档帧率定义为 SWF 播放时的每秒帧数，见 [Adobe Animate 文档属性说明](https://github.com/AdobeDocs/developers-animatesdk-docs/blob/master/Document_object/document_summary.md)。

## 2. 一个动作有多少帧：实际子片段样本

下表从角色动作标签所在的父帧追踪其显示列表，再读取对应子片段帧数。名义时长按 `N / 60` 计算，表示不变速、不中断且完整播放一次的时间轴长度；不代表整次战斗行动耗时。

| 角色导出名 | 动作标签 | 子片段 ID | 时间轴帧数 | 名义时长 |
|---|---|---:|---:|---:|
| `CatTest` | `idleF` | 9 | 180 | 3.000 秒 |
| `CatTest` | `hitF` | 481 | 13 | 0.217 秒 |
| `CatTest` | `shootF` | 559 | 45 | 0.750 秒 |
| `CatTest` | `heavyMeleeF` | 976 | 48 | 0.800 秒 |
| `CatTest` | `heaviestMeleeF` | 984 | 74 | 1.233 秒 |
| `CatTest` | `dyingF` | 483 | 77 | 1.283 秒 |
| `Rat` | `idleF` | 3442 | 100 | 1.667 秒 |
| `Rat` | `hitF` | 3443 | 13 | 0.217 秒 |
| `Rat` | `walkF` | 3444 | 31 | 0.517 秒 |
| `Rat` | `dashF` | 3452 | 15 | 0.250 秒 |
| `Rat` | `dyingF` | 3463 | 30 | 0.500 秒 |
| `Worm` | `portoutF` | 3385 | 50 | 0.833 秒 |
| `Worm` | `shootF` | 3393 | 30 | 0.500 秒 |
| `Pooter` | `shootF` | 3242 | 46 | 0.767 秒 |
| `Pooter` | `dyingF` | 3249 | 22 | 0.367 秒 |

`CatTest` 来源为 `catanis.swf`，另外三种角色来源为 `enemies.swf`。ID 仅在各自 SWF 内有效，不能跨文件当作全局资源编号。保留 F/B 等原始标签后缀，以避免未经验证的朝向解释。

同类标签不一定等长：Rat 的 `walkB` 是 30 帧，`walkF` 是 31 帧；Worm 的 `portoutB` 是 40 帧，`portoutF` 是 50 帧。不能只测一个方向就推断所有变体。

### 容易误判：父片段的帧数不等于动作帧数

Rat 的父片段是 30 帧，标签包含 `idleF`、`hitF`、`walkF`、`dashF` 等。这些帧承载动作选择入口，实际动作位于子片段中。Pooter 的父片段只有 14 帧，但 `shootF` 对应的子片段有 **46 帧**。

所以，“Pooter 射击只用了 14 帧”是错误统计方法。必须继续追踪标签对应的显示对象。父帧也可能同时包含多个对象；例如 Pooter 的 `deadF` 引用了多个子对象，不能把它们的帧数相加当成死亡时长。

## 3. 是状态机还是时间轴

资源证据支持“按动作名称选择入口，再播放嵌套时间轴”的解释。动作选择与帧播放解决不同问题，可以共同存在。

```mermaid
flowchart LR
    A[技能配置与角色状态] --> B[动画名称选择]
    B --> C[角色导出元件]
    C --> D[动作标签对应的父帧]
    D --> E[子片段时间轴]
    E --> F[显示列表与嵌套对象]
    F --> G[场景中的角色表现]
```

图中标签与子片段的关系来自资源解析；运行时如何锁定父帧、何时切换、允许谁打断谁，属于尚未还原的控制逻辑。动作标签本身并没有给出完整状态转换条件。不能据此认定原作采用某个具体 FSM、行为树、骨骼动画框架或虚幻 Anim Blueprint。

`swfs/swflist.gon` 列出 `catparts.swf`、`catanis.swf`、`catanis2.swf`、`enemies.swf` 等游戏资源，并有按文件配置的 `curve_resolution`。这说明 SWF 是游戏使用的资源格式，但不证明游戏嵌入 Flash Player，也不足以确定运行时采用矢量绘制、预先栅格化还是混合方案。

## 4. 技能如何选动画，伤害又在什么时候发生

`data/ability_templates/ability_templates.gon` 中，近战模板使用 `MeleeAttackAbility` 与动画 `Default`；远程模板使用 `RangedAttackAbility` 与动画 `shoot`，另配投射物、速度和抛物线高度。说明角色动作和投射物表现分别具有配置入口。

`data/abilities/basic_attacks.gon` 的基础近战配置包含 `damage_threshold_altanimations`，列出 `heavyMelee` 对应 10、`heaviestMelee` 对应 20。资源中也确实存在相应命名片段。这支持“依据伤害阈值选择不同近战动画”的判断；阈值边界是大于还是大于等于、最终覆盖优先级如何，仍需原生代码证据。

但 **45 帧的 shoot 片段不等于第 45 帧才发射，更不等于第 45 帧命中**。发射、飞行、碰撞/目标命中、受击与后摇可能处于不同时间段。本次没有识别出能可靠映射到具体动作帧的原生伤害提交点，所以不填造“第 12 帧发射”之类数字。

## 5. 60 帧时间轴为什么不等于 60 张画

SWF 的一个时间轴帧可以保留已有对象，也可以修改显示对象的变换、替换对象或改变显示列表。多个时间轴帧因此可能复用同一图形；嵌套片段还能在父对象内部继续播放。上述结构由 SWF 的显示列表和控制标签机制支持，见前述 Adobe 格式规范。

因此表中的 74 帧重击，表示 74 个时间轴节拍，不是“美术手绘了 74 张完全不同的猫”。要统计独立绘制数量，还需追踪图形引用并比较最终渲染画面；本次没有进行这一步。

同理，3 秒的待机片段只是资源长度，不证明角色每次待机都从头播完 3 秒才接受指令。循环策略、随机起播位置、提前切出、速度倍率都会影响实际观感，这些运行时细节不能从帧计数直接得出。

## 6. C++ 风格伪代码：动作选择与时间轴播放分离

以下只表达一种与资源结构兼容的实现方式。函数名、状态切换策略和时钟管理均为说明性设计，不是逆向恢复的原作代码。

```cpp
AnimationRequest ChoosePresentation(Ability ability, AttackContext context) {
    string animation = ability.graphics.animation;
    if (ability.hasDamageThresholdAnimations) {
        // 已知配置有 heavyMelee:10 和 heaviestMelee:20。
        // 原作的边界比较和优先级尚未确认，留作策略接口。
        animation = SelectByEngineThresholdPolicy(ability, context);
    }
    return ResolveExistingCharacterLabel(animation, context.visualVariant);
}

void EnterAction(AnimationRequest request) {
    CancelOrFinishPreviousPresentationByPolicy();
    parent.SeekToLabel(request.label);
    parent.HoldSelectedFrame();       // 本解释模型的父时间轴选择策略
    players = InstantiateChildren(parent.displayList);
    ResetChildrenAccordingToPolicy(players);
}

void TickPresentation(double dt, double speed) {
    if (paused || speed <= 0) return;
    accumulator += dt * speed;
    const double frameTime = 1.0 / 60.0;  // 来自本次 SWF 样本头
    while (accumulator >= frameTime) {
        accumulator -= frameTime;
        // 处理嵌套片段的显示列表变更和各自播放策略。
        AdvanceNestedTimelinesOneFrame(players);
    }
    DrawCurrentDisplayTree();
}
```

实际播放器必须为每个实例维护位置、生命周期与循环策略；同一片段的两个实例可能从不同时间开始。不能共享一个“全局当前动画帧”控制所有角色，也不能把所有嵌套子片段的长度相加。

以下演示同步模型同样属于设计建议：

```cpp
void PresentResolvedAction(ActionResult result, PresentationTrack track) {
    // 规则结果由计算层产生；表现层消费结果和表现事件。
    // 此处采用“先得到结果再演示”的方案，不声称原作顺序相同。
    StartCharacterClip(track.clip);
    SchedulePresentationEvents(track.events, result.id);
}

void AdvanceEvents(double oldTime, double newTime) {
    // 检查跨越区间，避免掉帧越过标记后漏发事件。
    for (Event e : EventsInInterval(oldTime, newTime)) {
        if (AlreadyDelivered(currentPlaybackId, e.id)) continue;
        DeliverVisualEvent(e);  // 发射、命中特效、音效等演示事件
        MarkDelivered(currentPlaybackId, e.id);
    }
}
```

起播时刻的事件需单独处理；循环用轮次区分事件；重新播放使用新播放 ID。拖动演示时间轴则重建画面，不重新结算伤害。死亡或受击打断动作后，遗留的投射物和回调需要按既定策略结束，避免访问已失效对象。这些是实现可靠演示系统应处理的问题，并非本次已验证的原作内部策略。

## 7. 辅助理解的动画演示面板应显示什么

建议按“角色 → 动作标签 → 子片段”逐级选择，并同时显示父帧、子片段 ID、总帧数、当前帧、名义时间、播放倍率与嵌套显示对象数量。播放控制包括暂停、单帧步进和从头播放。这样可以直观看见“父片段选动作，子片段播动作”。

适合比较的三个样本是 Rat `hitF` 的 13 帧、CatTest `heavyMeleeF` 的 48 帧，以及 `heaviestMeleeF` 的 74 帧。面板还应区分“资源标签”和“人为添加的演示事件”，不得把自定义命中标记显示成原作证据。本仓库本轮交付为分析文档，没有实现可运行播放器。
