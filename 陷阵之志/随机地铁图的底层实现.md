# 随机地铁图的底层实现

这里讨论《陷阵之志》的单场战斗地图。标题沿用用户指定名称；岛屿上的任务路线与战斗棋盘是不同层次，本文不把它们混为一个生成算法。

## 核心方式：预制布局与局部随机变化

本机安装目录有 376 个 `.map` 文件，声明尺寸全部为 8×8，包括特殊地图和测试用途地图，不能等同于 376 张普通战斗地图。

地图文件已经写有坐标、地形、建筑属性、任务标签 `tags` 和命名区域 `zones`。例如 `maps/acid0.map` 包含 `generic`、`acid`、`acid_pool`、`pistons` 标签，以及可供活塞任务使用的候选点区域。这表明基本空间布局是预先保存的，而不是每次从空棋盘任意摆放山体与建筑。

开发者 Justin Ma 的公开说明与本机资源相符：基本布局人工设计，森林、沙地及任务特有建筑位置采用程序变化，以降低令人难以处理的地形组合出现概率。[开发者采访](https://www.gamedeveloper.com/design/devs-weigh-in-on-the-best-ways-to-use-but-not-abuse-procedural-generation)

## 地图与任务如何结合

任务脚本声明自己需要的 `MapTags`。`Mission:GetMapTag()` 遇到标签数组时随机取一个；遇到单个标签则直接返回。另外，`Mission:GetMap()` 会从 `MapList` 中随机选择一项。这是两处已确认的脚本接口，不能据此断言所有任务都依次执行这两条路径。

以坦克任务为例，`mission_tanks.lua` 使用 `satellite` 标签，开局调用 `AddDefended()`。后者从地图的同名区域取位置并放置任务单位。因此，标签负责描述“什么地图适合这个任务”，区域负责描述“任务内容允许放在哪里”。

下面是整体流程的 **C++ 风格概念伪代码**。`引擎选择兼容地图` 和 `应用局部变化` 代表尚未完整逆向的引擎逻辑，不表示已确认其抽样概率或具体调用顺序。

```cpp
BattleMap PrepareBattle(Mission mission) {
    string tag = mission.MapTags.isArray()
        ? RandomElement(mission.MapTags) // 已确认的 GetMapTag 语义
        : mission.MapTags;

    // 概念占位：标签如何与岛屿、历史选图等条件组合，尚未完全确认。
    MapTemplate base = 引擎选择兼容地图(mission, tag);
    BattleMap board = LoadLayout(base);

    // 开发者确认有局部随机变化；具体实现未全部恢复。
    应用局部变化(board, mission);

    // 各任务自己的脚本，可使用 base.zones 提供的位置。
    mission.StartMission(board);
    return board;
}

// 另一处明确的脚本接口；不是断言上述流程必定调用此函数。
MapName GetExplicitMap(Mission mission) {
    return mission.MapList[RandomInt(mission.MapList.size())];
}
```

## 为什么每局仍然不同

基本地形模板、任务类型、局部地形、任务物件及敌人配置共同影响战局。模板相同，不代表任务物件或敌人也相同；也不能把不同的战局都当作全新生成的地图布局。

```cpp
struct MapTemplate {
    Size dimensions;
    List<FixedTile> terrainAndBuildings;
    Set<string> tags;
    Dictionary<string, List<Point>> zones;
};

// 这是帮助理解的数据模型，并非原作 C++ 类型定义。
```

## 证据与未确认部分

本机证据：`maps/*.map`、`scripts/missions/missions.lua` 的 `GetMapTag` / `GetMap` / `AddDefended`、`scripts/missions/grass/mission_tanks.lua`。

没有完整确认最终抽图权重、地图去重策略、旋转镜像规则、原随机数发生器、种子调用顺序及岛屿任务路线生成过程。本文伪代码不能生成与原游戏逐种子一致的结果。
