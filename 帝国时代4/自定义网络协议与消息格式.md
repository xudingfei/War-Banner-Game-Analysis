# 帝国时代 IV：自定义网络协议与消息格式

检查日期：2026-09-13。这一篇进一步分析原作的消息读写代码，不再只讨论通用网络同步设计。

**本次已确认部分原作二进制消息格式：同步消息的 `0x20` 类型字节、消息体的长度布局，中继层的 `0x0A` 数据容器、`0x14` 探测消息和 `0x15` 握手/恢复消息，以及相关连接状态与计时条件。** 这些是客户端代码证据，尚未通过线上抓包确认完整封装关系。

## 1. 这次怎么确认的

先从 EXE 的报错字符串、虚表和异常处理元数据定位函数。磁盘文件中的部分关键函数无法可靠地连续反汇编，因此通过 Steam 正常启动游戏，只读读取对应的运行时代码范围，再核对函数的读写行为。

没有进入多人对局，没有调用游戏内部函数，没有注入或写入进程内存，没有发送自造数据包，也没有读取会话密钥值。读取运行时代码不等于跟踪到这些函数在某场网络对局中实际执行。

然后依据确认的同步消息布局，对本地回放中的记录进行离线解析和重新编码：

| 样本 | 同步消息数 | 消息内的数据块数 | 重新编码与原记录比较 |
|---|---:|---:|---|
| `temp.rec` | 8,202 | 2,444 | 逐字节一致 |
| `temp_campaign.rec` | 3,035 | 2,982 | 逐字节一致 |
| 合计 | 11,237 | 5,426 | 全部通过 |

这是对**内部消息布局**的交叉验证，不是对服务器互通性的验证。原作代码片段、进程代码页和用户回放均不提交到仓库。

## 2. “自己的协议”分在哪几层

| 层次 | 本次看到的内容 | 不能混淆的地方 |
|---|---|---|
| 传输实现 | Socket 抽象、WebSocket 相关代码与可选路径 | 未确认当前对局最终使用的 TCP/UDP/WebSocket 组合 |
| 中继消息 | `0x0A`、`0x14`、`0x15` 的首字节分派 | 这里按整个字节区分类型 |
| 游戏同步消息 | 写入 `0x20`，读取时取高 4 位，类型为 2 | 不是把 `0x20` 当作协议版本 32 |
| 具体游戏命令 | 同步消息内嵌不透明字节负载 | 移动、建造等命令还有各自格式 |

这两组类型号属于不同的读写上下文。本次没有跟完所有适配层，不能直接断言网络上的每个 `0x0A` 子项都恰好包着一个 `0x20` 消息。TLS/WebSocket 或其他传输封装也可能在它们之外。

## 3. 游戏同步消息：已核对的精确布局

`GameMsgSyncCommand` 的输出路径先写入一个字节 `0x20`，然后调用消息体写入函数。输入路径先读取一字节，执行 `header >> 4`，当结果为 2 时读取对应消息体。低 4 位在该入口没有进一步解释，不能自行命名为压缩或可靠传输标志。

该入口使用原始字节流分支。当前 Windows x64 样本直接复制整数内存字节，因此下表中的多字节整数按小端解释。

| 相对消息起点偏移 | 长度 | 字段 | 含义与证据 |
|---:|---:|---|---|
| `0x00` | 1 | `header` | 本次写入器固定写 `0x20`；读取器检查高 4 位 |
| `0x01` | 4 | `field0` | 回放样本中对应递增的逻辑 tick 编号 |
| `0x05` | 4 | `field1` | 未确认语义；不能直接命名为 CRC/ACK/随机种子 |
| `0x09` | 4 | `blockCount` | 后续数据块数量 |
| `0x0D` 起 | 可变 | `blocks[]` | 每块布局如下 |

每个数据块：

```text
uint64  blockMeta       // 8 字节，业务含义未完整确认
uint32  payloadLength   // 4 字节，后续负载字节数
byte    payload[payloadLength]
```

因此消息总长度为：

```text
13 + Σ(12 + payloadLength[i]) 字节
```

没有数据块时仍然可以形成 13 字节消息，不能因为没有单位操作就推断客户端不再产生同步记录。

此前回放格式研究将 `blockMeta` 拆成两个 32 位字段。本次读写函数实际按 8 字节整体处理；可以保留旧研究的解释线索，但暂时不应把其中某一半断言成网络客户端 ID。

用于解释的空消息样本：

```text
20 | 64 00 00 00 | 44 33 22 11 | 00 00 00 00
     tick = 100    未知字段示例    blockCount = 0
```

这些是人工示例值，没有向游戏发送。它展示一个内部消息体，不包含完整线上协议的其他层。

### 从原作读写逻辑整理的 C++ 伪代码

以下字段顺序来自反汇编；有意义的函数名和边界检查是为了说明而补充，不是原作源码。负载保持原样，不猜测其内部每条命令。

```cpp
SyncMessage DecodeSyncMessage(ByteSpan bytes) {
    Reader r(bytes);
    SyncMessage m;
    m.header = r.ReadU8();
    Require((m.header >> 4) == 2);
    m.tickLike = r.ReadU32LE();
    m.unknown32 = r.ReadU32LE();
    uint32 count = r.ReadU32LE();
    Require(count <= r.Remaining() / 12);
    for (uint32 i = 0; i < count; ++i) {
        uint64 meta = r.ReadU64LE();
        uint32 length = r.ReadU32LE();
        Require(length <= r.Remaining());
        m.blocks.Add(meta, r.ReadBytes(length));
    }
    Require(r.Remaining() == 0); // 示例约定：输入恰好包含一条消息
    return m;
}

void EncodeSyncMessage(const SyncMessage& m, Writer& w) {
    w.WriteU8(0x20);            // 此处对应观察到的原作写入常量
    w.WriteU32LE(m.tickLike);
    w.WriteU32LE(m.unknown32);
    w.WriteU32LE(CheckedU32(m.blocks.Count()));
    for (const auto& b : m.blocks) {
        w.WriteU64LE(b.meta);
        w.WriteU32LE(CheckedU32(b.payload.Size()));
        w.WriteBytes(b.payload);
    }
}
```

消息体函数还支持另一类流接口。本篇只还原由已定位 `GameMsgSyncCommand` 入口使用的原始字节流分支，不把另一分支的表示方式混入此表。

## 4. 中继层的三种消息

### `0x14`：9 字节的时间探测消息

写入函数先设置类型 `0x14`，随后在偏移 1 写入 8 字节时间值：

```text
offset 0: uint8  type = 0x14
offset 1: uint64 timestamp
总长：9 字节
```

调用方的时间来自高精度计数器换算的毫秒值，不是已确认的 UTC 时间戳。接收分派遇到 `0x14` 会走维护连接活性的路径；本次没有跟到独立的 RTT 计算，故称“探测/保活消息”，不把它称为游戏命令 ACK。

### `0x15`：连接建立与恢复用的握手消息

在创建新 Socket 并发起连接的路径中，构造类型 `0x15` 的对象。首次连接分支设置状态值 0，恢复相关分支设置状态值 2；写入器根据这个字段选择是否附加一个 32 位字段。

本次观察的构造路径把消息版本字段设为 5。该版本下的布局如下，未知字段使用中性名称：

| 字段 | 状态不等于 2 时偏移 | 状态等于 2 时偏移 | 长度 |
|---|---:|---:|---:|
| 类型 `0x15` | 0 | 0 | 1 |
| 标识组合值 | 1 | 1 | 8 |
| 会话相关字段 B | 9 | 9 | 8 |
| 状态字节 | 17 | 17 | 1 |
| 恢复相关字段 | 无 | 18 | 4 |
| 消息版本 | 18 | 22 | 2 |
| 超时覆盖字段 | 20 | 24 | 4 |
| 会话相关字段 C | 24 | 28 | 8 |
| 合计 | **32 字节** | **36 字节** | |

标识组合函数把来自 `RL_TITLEID` 的 16 位值左移 48 位，再与另一个 64 位输入按位或。后一个输入的范围约束未跟完，不能擅自补上源码中没有看到的掩码。

版本相关写入是条件性的：版本大于 0 时写版本及超时覆盖字段，版本至少为 5 时再写最后的 8 字节字段。不能把上表当作所有历史版本通用的固定握手长度。

程序另有诊断文本提到 session、secret、reconnectState、clientMessageVersion 和 timeoutOverride，但本次没有逐一证明诊断文本参数与所有表格字段的对应关系。因此 B/C 不强行命名为具体令牌，也不展示任何实际凭据。

### `0x0A`：带计数和长度的数据容器

这一类型的写入函数与中继接收分支相互印证。当前分支的主要布局为：

```text
uint8 type = 0x0A
uint8 fieldA                     // 语义未确认
uint8 entryCount
repeat entryCount:
    uint8 entryTag               // 语义未确认
    uint16 payloadLength        // 当前样本原始小端复制
    byte payload[payloadLength]
uint8 smallValueCount
byte smallValues[smallValueCount] // 各字节语义未确认
if messageVersion > 1:
    uint16 extraLength
    byte extra[extraLength]
```

这里的 messageVersion 来自对象/上下文，并非又在上述容器中读了一个版本字段。被检查的中继接收分支初始化该值为 5，所以会处理最后的扩展负载。

原作写入器检查单项负载和扩展负载不超过 `0xFFFF`。接收路径也逐项检查长度范围，并可继续处理同一接收缓冲中剩余的数据容器。这支持“数据可成批封装”的判断；`smallValues` 不能仅凭形状认定为 ACK 列表。

中继读取接口传入 `0xFFFF` 的缓冲上限，循环还有每次处理最多 1,000 次成功读取的限制。**这些是该代码路径的缓冲与循环预算，不是互联网 MTU、每秒包数或 TCP 报文长度。** 底层接口可能已经做过消息分帧，本次未跟完。

## 5. 已确认的连接状态与时间常量

状态值与字符串映射来自中继状态格式化函数，而非根据数字猜测：

| 数值 | 状态 |
|---:|---|
| 0 | DISCONNECTED |
| 1 | CONNECTING |
| 2 | CONNECTED |
| 3 | DISCONNECTING |
| 4 | SHUTDOWN |

以下常量来自同一中继处理路径中的比较和加法，单位由高精度计数器乘 1,000 再除以频率确认：

| 数值 | 代码中实际用途 | 不能解释成 |
|---:|---|---|
| 125 ms | 两次处理调用间隔超过此值进入诊断路径 | 发包频率固定 8 Hz |
| 1,000 ms | 尝试建立新 Socket 后设置下一次重试时间门槛 | 每秒重发全部游戏命令 |
| 3,000 ms | 空闲探测截止时间；收到数据后更新，也在该探测发送后更新 | 所有游戏心跳统一为 3 秒 |
| 30,000 ms | 另一条周期性发送 `0x14` 的时间门槛 | 对局必定 30 秒踢人 |
| 40,000 ms | 无覆盖值时设置的较长恢复窗口截止时间 | 所有模式保证可断线 40 秒 |

短超时窗口使用对象中的配置值，存在非零 timeoutOverride 时优先使用它；较长窗口在覆盖分支采用覆盖值的 5 倍。这些截止时间在连接建立或收到数据时设置/更新，因此不能把 40 秒理解为“检测到断线后再额外等待 40 秒”。收到数据后也会更新 3 秒空闲探测时间。

连接处于 CONNECTED 且短超时到期时，路径请求断开，转入 DISCONNECTING，并清除下一次重试时间。回到 DISCONNECTED 后，只有在允许恢复、仍处于较长时间窗口且重试门槛已过时才创建新 Socket；否则可进入 SHUTDOWN。真实动作还受底层 Socket 状态和回调影响。

这比“无限发心跳就不会断线”更接近本机代码：**它维护有截止时间的状态机，尝试恢复有限时长的中断，条件不满足则停止。** 握手中确实有恢复分支，但仍不能据此声称进程崩溃后一定能恢复整场对局。
