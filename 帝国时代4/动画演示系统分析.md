# 帝国时代 IV：动画演示系统分析

检查日期：2026-09-13。依据本机动画资源、SCAR 接口文档、参考武器属性、画质配置及动画团队的一手访谈。此处“演出”包含单位动作、战斗效果及脚本控制的表现，未全面分析战役影片播放系统。

**可以确认原作有动画状态机接口、独立的表现层 State Tree 调度，以及包含骨骼和压缩动画的资源。** 它使用 Relic 的 Essence Engine；资源里的 `.abp` 不能直接理解为虚幻 Animation Blueprint。

## 1. 资源层：骨骼、动作集合和外观组装

本次读取 `cardinal/archives/ArtCivilizations.sga` 的目录，得到 951 个文件条目，包括 79 个 `.rhka`、79 个 `.rootmotion`、9 个 `.abp`，以及 `.rgo`、`.rpb` 等文件。这个包的数量不代表全游戏动画总数。

具体检查的动画文件：

```text
art/civilizations/common/humans/archetypes/base_archer/base_archer.rhka
```

解压长度为 **7,094,476 字节**。文件中读到 `TAG0`、`SDKV20180200`，以及 `hkaSkeleton`、`hkaAnimationBinding`、`hkaAnimation`、`hkaPredictiveCompressedAnimation`、`hkaAnnotationTrack` 等类型名。

这些是骨架、动画绑定、压缩动画及注释轨道的直接资源证据。文件还包含 `duration`、`numFrames` 成员名，但本次没有把对象布局完整解码并对应到具体动作，不能从成员名旁边随便读一个整数就当作帧数。

名称支持按武器、方向和动作类型组织资源的判断；本次没有渲染这些片段，不能仅凭命名认定每个动作最终如何选中或视觉上完全符合名称。

检查的 `bow_arbalest.abp` 是短文本，其 `model` 列表引用基础 arbalest archetype 与外观资源。这是本机外观/原型组合的证据，不能因为扩展名相同就套用 UE 的动画蓝图机制。

## 2. 它是否使用状态机：接口已经给出直接答案

安装目录的 `scardocs/html/function_list.htm` 明确提供以下接口：

| 接口 | 文档说明支持的用途 |
|---|---|
| `Entity_SetAnimatorState(entity, stateMachineName, stateName)` | 设置实体某个动画状态机的状态 |
| `Entity_SetAnimatorVariable(entity, variableName, value)` | 设置动画数值变量 |
| `Entity_SetAnimatorAction(entity, actionName)` | 触发动画动作 |
| `Entity_SetAnimatorEvent(entity, eventName)` | 发送动画事件 |
| `Entity_SetAnimatorActionParameter(...)` | 设置动画动作参数 |
| `StateTree_QueueGlobalStateTreeEntity(keepAlive, openingBranchName, entity)` | 为实体排队运行全局状态树 |

这些文档对直接设置 Animator 的接口提示仅用于简单动画。它们证明状态机、动作、变量和事件接口存在，但没有公开整棵战斗动画图。

State Tree 文档则明确说：任务在合适时机启动，全局树有独立生命周期，可以与目标上的其他状态树分开运行，`keepAlive` 控制结束后是否重新启动。接口来源路径属于引擎 `presentation` 模块。

本机 `Data.sga` 也存在 `statetrees/simulation/statetree.bin`、`statetrees/viz/statetree.bin`、`statetrees/speech/statetree.bin` 等路径。路径名称说明资源有不同类别；本次没有解码这些二进制图，不能把每一类都当作纯骨骼动画图。

因此更准确的理解是：**游戏行为与表现任务决定做什么，Animator 状态/变量决定选什么动作，动画播放器负责采样骨骼姿态。** State Tree、动画状态机和动作片段是不同层级，也不是“用了状态机就不能用时间轴”。

## 3. 原作动作是怎样制作的

Relic 动画总监 Brent Breedveld 在 Animatrik 的一手访谈中说明，人类和马匹/骑手动作采用了动作捕捉；团队先建立马模型及骨架，再把动作重定向到 MotionBuilder 中的 rig。战斗与能力还有额外骑手动作层，最终进入 Essence Engine。访谈也提到，把源动作接入游戏模拟是主要难点。见 [动画总监访谈](https://www.animatrik.com/blog/enhancing-gameplay-with-horse-mocap-in-age-of-empires)。

这与本机骨骼/压缩动画资源相互印证。动作捕捉是内容制作方式，状态机是运行时组织方式，两者并不冲突。访谈中的“动作层”也不能自动证明每个运行时节点采用某种特定的加法混合算法。

## 4. 一个动作用多少帧

本次没有可靠解出单个 `.rhka` 片段的 `numFrames`、持续时间和采样率，因此不提供猜测的“弓箭手射击 30 帧/60 帧”。需要继续解码动画对象及其绑定，或者在可用查看器中逐片段读取这些元数据。

应分别记录四个概念：

| 概念 | 本次证据状态 |
|---|---|
| 原始动作捕捉采样率 | 未取得具体数值 |
| 压缩动画片段的采样点/帧数 | 读到相关类型和字段名，未完成逐片段解码 |
| 战斗规则中的瞄准、发射、恢复计时 | 参考武器配置有明确字段，可检查 |
| 屏幕实际渲染 FPS | 本次未运行性能测量 |

骨骼动画可以在时间点之间插值采样。假设某个演示片段有 31 个等间隔采样点、采样率为 30 Hz，且首尾点都存储，那么首末点跨度为 `(31-1)/30 = 1 秒`。这是公式示例，不是本机动作统计；是否保留循环端点也取决于格式。

## 5. 战斗计时如何连接动画

本机参考属性 `instances/weapon/races/common/ranged/weapon_archer_2.xml` 中可见：

| 配置分组/字段 | 基础参考值 | 应如何解读 |
|---|---:|---|
| `aim.fire_aim_time.min/max` | 0.25 / 0.25 | 瞄准阶段计时参数 |
| `fire.wind_up` | 0 | 起手相关参数 |
| `fire.wind_down` | 0.5 | 发射后阶段相关参数 |
| `fire.animation_impact_frame_time` | 0.5 | 动画 impact 时序字段；具体单位/归一化语义未追到原生实现 |
| `reload.duration.min/max` | 0.75 / 0.75 | 装填阶段计时参数 |
| `anim_table.state_name` | `ranged_weapon_state` | 武器配置连接动画状态的名称 |
| `anim_table.attack_speed_scale_value` | 1 | 动画速度缩放相关参数 |

`weapon/races/english/ranged/weapon_archer_2_eng.xml` 继承这个基础武器，并覆盖部分数值。还有 campaign、xp3 等变体，不能把上表写成当前所有模式的最终弓箭手攻速。

**这些计时值不能直接相加成准确的攻击周期，更不能换算成已确认的动画帧数。** 瞄准、发射、装填之间可能有条件和重叠，移动、换目标、升级也可能改变过程；完整状态转换和倍率计算仍需原生规则证据。

该基础配置的一些动画字段为空字符串。不能因为 schema 支持横向追踪、目标距离等变量，就断言这个样本已经启用所有变量。

## 6. 连贯演出要解决哪些问题

结合证据，可以把职责理解为下面的结构。箭头是解释模型，不是反编译出的完整调用图。

```mermaid
flowchart LR
    A[命令、目标与战斗模拟] --> B[行动阶段与规则事件]
    B --> C[表现 State Tree]
    C --> D[Animator 状态、动作、变量]
    D --> E[骨骼片段采样与混合]
    E --> F[蒙皮角色与武器显示]
    B --> G[投射物、音效与命中特效]
    G --> F
```

从实现设计看，移动方向和速度需要与走跑动作匹配；骑手和马应保持协调；受击或死亡会影响当前动作；箭矢飞行与命中特效也要和战斗结果对齐。原作资源与接口提供了支持这些工作的基础，但本次没有确认每项功能的具体混合树、IK 算法或 root motion 使用策略。

`.rootmotion` 文件的存在只能说明有相关数据，不能证明所有单位都由动画根骨驱动寻路位置。RTS 中“规则层决定位置，表现层适配动作”是一种合理设计，文中伪代码采用它，但不把它冒充已经还原的原作全局规则。

## 7. 大量单位的动画成本

本机 `sysconfig.lua` 提供独立的 `animationquality` 设置，列出 Low、Medium、High、Very Low 四档。另一段预设注释说明 AnimationQuality 用于控制动画系统的目标负载。

这能确认动画有单独的质量/负载调节入口。不能进一步凭此声称“远处单位固定 15 FPS、近处固定 60 FPS”，因为距离阈值、调度频率、裁剪与骨骼层级策略没有在本次读出。该预设也不代表用户当前使用的设置。

自己的实现可以按屏幕重要性分配更新预算，降低不可见单位的姿态更新频率，同时保持规则模拟一致；这属于设计建议。

## 8. C++ 风格伪代码：模拟和表现分别推进

以下是可借鉴到 C++ / ECS 计算层与蓝图表现层的结构，不是原作源码，也不声称原作采用 UE 或同样的 ECS 框架。

```cpp
void SimulationTick(FixedDelta dt) {
    UpdateMovementAndTargets(dt);
    for (Attack& attack : activeAttacks) {
        AdvanceAttackPhase(attack, dt);
        if (CrossedFireBoundary(attack) && !attack.fireCommitted) {
            attack.fireCommitted = true;
            SpawnLogicalProjectileOrResolveAttack(attack);
            EmitPresentationEvent(attack.id, Event::Fire);
        }
    }
}

void PresentationTick(double dt) {
    for (UnitView& view : visibleViews) {
        auto state = ReadSimulationView(view.entityId);
        view.animator.SetVariable("visual_speed", state.speed);
        view.animator.SetState(ChooseVisualState(state));
        view.animator.ConsumeEvents(GetPendingViewEvents(view.entityId));
        view.pose = SampleAndBlendClips(dt, view.animator);
        RenderSkinnedUnit(view.pose, state.interpolatedPosition);
    }
}
```

`visual_speed` 和其他函数名是示例。攻击事件需要去重，死亡/换目标后要处理旧回调；暂停、加速和低帧率下应检查跨越的时间区间。表现降频不能让逻辑层少算伤害，也不能通过重启动画重置攻击冷却。

若制作辅助理解的演示面板，建议同时显示逻辑攻击阶段、Animator 状态、片段时间、混合权重、速度倍率和发射/命中事件。只有把这些轨道放在同一时间轴上，才能判断“动画看着已射出”与“规则已提交攻击”是否一致。
